# 变砖风险评估与安全协议

设备：`yingtian` / `M367FC`，Android 17，当前 slot `_b`，引导程序 **green（锁定）**，
SELinux **Enforcing**。数据来自设备实测（2026-10-25）。

## 1. 结论先说

在这台机器上，**本项目的所有代码都不具备"变砖"的能力**，原因是它根本不满足变砖的前提：

| 变砖需要什么 | 本项目是否有这个动作 |
| --- | --- |
| 写 `boot_a/boot_b`、`init_boot_*`、`vbmeta_*` | 没有。只有 `adb install` 与自己进程的内存 |
| 写 `xbl/abl` 等引导链分区 | 没有 |
| `fastboot flash` / `fastboot oem` / `fastboot set_active` | 没有（引导程序锁定，本来也会拒） |
| `dd` 到 `/dev/block/*` | 没有 |
| 修改 `persist` / `modem` / `misc` / `devinfo` | 没有 |
| 关闭验证启动 / 改 `ro.boot.*` | 没有（只读读取） |

**引导链是签名校验的**：即使 `/data` 或内核内存被写坏，关机重启后仍然是引导程序先跑、
校验 `boot_b` 的签名、加载原厂内核。开机链不在我们的写入范围内，所以"打不开"这个
级别的损坏在当前动作集合里不会发生。

## 2. 真实存在的风险（按概率排序）

| 风险 | 概率 | 后果 | 恢复方式 |
| --- | --- | --- | --- |
| 内核 oops → panic → 重启 | 高（一旦开始碰内核内存） | 重启回到原厂内核 | 什么都不用做；`mi_mtdoops` 会把 oops 落到 `oops` 分区 |
| panic 后卡住不自动重启 | 中 | 屏幕黑/停住 | **长按电源键 10~15 秒**强制重启 |
| 内核内存写坏导致 `/data` 文件系统元数据损坏 | 中低 | 开机卡 logo / bootloop | 恢复模式「清除数据」→ 设备可用但数据丢失 |
| 内核内存写坏导致系统分区只读损坏 | 低 | bootloop | 官方线刷（BL 锁定只能刷官方包，反而更稳） |
| 彻底无法进入任何模式（真砖） | **极低** | 需要售后 | —— |

这台机器还为崩溃做了准备：`mi_mtdoops.devname=/dev/block/by-name/oops`（独立 oops 分区）、
`pstore.compress=none`（pstore 可用）、A/B 双槽（`boot_a` sdc22 / `boot_b` sdc57）。
内核崩溃在这类工程构建上属于**被预期、被记录**的事件。

## 3. 硬性禁令（写进流程，不靠自觉）

1. 任何阶段都**不写块设备**：禁止 `dd of=/dev/block/*`、禁止 `mount -o rw,remount /`、
   禁止 `fastboot flash`。
2. 不碰 `/data/adb`、不装 Magisk/KernelSU 模块、不写开机自启。
3. 不在 `boot_completed != 1` 或 `getenforce != Enforcing` 的状态下继续实验。
4. 每次破坏性运行前必须留快照（`scripts/safety_preflight.sh snapshot`），运行后核对。
5. 一次只跑一个实验进程，带超时；不允许并发多进程同时写内核。
6. 出现 panic 后**先停下**，等设备自己回来并核对状态，再决定下一步。

## 4. 恢复阶梯

```
① 自动重启          → 等 30 秒，设备会自己回到系统
② 长按电源 10~15 秒  → 强制断电重启（panic 卡死时用这个）
③ 恢复模式           → 音量上 + 电源；选「清除数据」可救 bootloop（会丢数据）
④ MiAssistant / 线刷 → BL 锁定只接受官方包，刷回去即可
```

## 5. 对工作连续性的影响（重要）

本工具链的 shell 运行在**平板自身**的 PalmCode 环境里。**设备一重启，这个环境会一起退出**，
adb 的 loopback 连接（`127.0.0.1:45305`）也可能需要重新配对。

因此进入破坏性阶段前必须做到：

- 所有代码与文档已推到 GitHub（当前 `main` 分支已包含全部内容）；
- 关键命令与预期输出已写进文档，重启后可从仓库直接续做；
- 不把"未提交的成果"留在设备内存里。

## 6. 当前能力边界（截至 2026-10-25）

| 阶段 | 是否已实现 | 是否能弄坏设备 |
| --- | --- | --- |
| 环境探测 / 闸门 / BTF 布局 | 是 | 否（只读） |
| 定时器可达性测量（`trprobe`） | 是 | 否（只操作自身进程的定时器） |
| 提权执行（内核内存写入 / 凭据改写） | **否** | —— |
| rootd 授权层 | 是（需要已有 root 凭据才可用） | 否 |

**也就是说：今天这套东西跑一万次也炸不了你的平板**，因为它连一行内核写都没有。
真正需要评估变砖风险的是"下一步要写的利用阶段"。
